Reference Document

Data Dictionary

All tables and fields in artemis2.duckdb. Four tables share a common timestamp spine at 1-minute cadence across the ~9-day Artemis II mission window. The dataset originates from the JPL Horizons ephemeris system and covers the period from first DSN acquisition through reentry plasma blackout.

Provider
NASA Jet Propulsion Laboratory — Solar System Dynamics Group
Endpoint
ssd.jpl.nasa.gov/api/horizons.api
Documentation
ssd.jpl.nasa.gov/horizons/manual.html
Data Type
High-precision ephemeris — position, velocity, orbital elements — reconstructed from Deep Space Network tracking solutions.
Architecture

Data Pipeline

Ingest → Storage → Runtime
JPL Horizons API │ ▼ scripts/fetch_horizons.py ← pulls raw ephemeris (VECTORS or ELEMENTS) │ ▼ scripts/init_db.py ← parses, validates, writes to DuckDB │ ▼ data/artemis2.duckdb ← four tables, 12,836 rows each │ ▼ app/db.py ← loads all tables into in-memory DuckDB at startup │ ▼ app/sql.py ← creates derived metric views on the in-memory connection

The on-disk DuckDB file is a reproducible artifact — re-run scripts/init_db.py to rebuild it from scratch. At runtime, all four tables are loaded into an in-memory DuckDB instance and extended with derived metric views. The data/ directory is gitignored.

Dataset 1 — Spacecraft State Vectors

Orion Capsule Trajectory

Cartesian state vectors for the Orion capsule in an Earth-centered inertial frame. Provides position, velocity, range, and range-rate at each timestep. This is the primary table for computing derived physics — speed, orbital energy, closest approach, and all trajectory arc rendering.

Query Parameters
ParameterValueNotes
COMMAND -1024 Orion spacecraft (Artemis II)
EPHEM_TYPE VECTORS Cartesian state vectors (position + velocity)
CENTER 500@399 Earth geocenter as origin
REF_SYSTEM ICRF International Celestial Reference Frame
REF_PLANE FRAME XY plane aligned to ICRF (equatorial)
OUT_UNITS KM-S Kilometers and km/s
VEC_TABLE 3 Position + velocity + light time + range + range rate
STEP_SIZE 1m 1-minute intervals
START_TIME 2026-Apr-02 01:59First available post-launch tracking point
STOP_TIME 2026-Apr-10 23:54Final point before reentry plasma blackout
CSV_FORMAT YES Comma-separated output for deterministic parsing
VEC_LABELS NO Labels suppressed; columns parsed positionally
Design Rationale
VECTORS type
Cartesian state vectors (X, Y, Z, Vx, Vy, Vz) in a fixed inertial frame — the natural representation for computing derived physics such as range, speed, orbital energy, and closest approach without angular ambiguity.
500@399 (geocenter)
Sets the coordinate origin at Earth's center of mass. All X/Y/Z values are Earth-centered distances in km — the most intuitive frame for visualizing launch, TLI, lunar flyby, and reentry from a mission control perspective.
ICRF / FRAME plane
The International Celestial Reference Frame is a fixed, non-rotating inertial frame tied to distant quasars. Z-axis aligns to the ICRF pole (close to Earth's north celestial pole), not the ecliptic. Standard for spacecraft navigation; stable regardless of Earth's orbital position.
VEC_TABLE=3
Includes all five useful output columns beyond the calendar/JD timestamps: position, velocity, light time, range, and range rate. Light time (lt_sec) and range rate (rr_kms) simulate DSN tracking observables in the dashboard.
1-minute step
~12,800 rows across the ~9-day mission window — fine-grained enough to resolve events like TLI, lunar closest approach, and the reentry corridor accurately, without the dataset becoming unmanageable.

lt_sec DOUBLE secondsOne-way light time from observer to spacecraft. Simulates DSN ranging observable.
rg_km DOUBLE km Range (distance) from observer to spacecraft. Equivalent to √(x²+y²+z²) for a geocenter observer.
rr_kms DOUBLE km/s Range rate (radial velocity). Negative = closing; positive = receding. Simulates Doppler observable.
jd_tdb vs datetime_utc: Horizons returns calendar timestamps in UTC but Julian Dates in TDB. The ~65-second difference is negligible for visualization but matters for precision physics involving relativistic corrections. Use datetime_utc for display; use jd_tdb if computing against other Horizons-sourced ephemerides (e.g., Moon position), since both share the same TDB epoch.
Dataset 2 — Osculating Orbital Elements

Orion Orbital Elements

Same query window and spacecraft as Dataset 1, with EPHEM_TYPE=ELEMENTS. Horizons computes osculating Keplerian orbital elements at each timestep using its full n-body solution — more precise than deriving them manually from the state vectors. This is the preferred source for orbital mechanics metrics (eccentricity, inclination, periapsis, etc.) where both tables cover the same period.

ColumnTypeUnitsDescription
datetime_utcTIMESTAMP— Calendar date/time, UTC. Join key.
jd_tdb DOUBLE days Julian Date, TDB.
ec DOUBLE — Eccentricity. Values > 1 indicate a hyperbolic trajectory (post-TLI). Filter ec < 1 before using ad_km or pr_d.
qr_km DOUBLE km Periapsis distance — closest approach to Earth center.
inc_deg DOUBLE deg Inclination relative to ICRF equatorial plane.
om_deg DOUBLE deg Longitude of ascending node (Ω).
w_deg DOUBLE deg Argument of periapsis (ω).
tp_jd DOUBLE days Time of periapsis passage (Julian Date, TDB).
n_deg_d DOUBLE deg/dayMean motion.
ma_deg DOUBLE deg Mean anomaly.
ta_deg DOUBLE deg True anomaly (ν) — current angular position in the orbit.
a_km DOUBLE km Semi-major axis.
ad_km DOUBLE km Apoapsis distance. Undefined for ec > 1 — Horizons returns a sentinel value. Always filter on ec < 1.
pr_d DOUBLE days Orbital period. Undefined for ec > 1 — no closed orbit exists on a hyperbolic trajectory.
Hyperbolic caveat: Once Orion is on a trans-lunar trajectory (eccentricity > 1), apoapsis (ad_km) and orbital period (pr_d) are physically undefined — there is no farthest point and no closed orbit. Horizons returns sentinel values for these columns during hyperbolic phases. Always filter on ec < 1 and use errors='coerce' before using these fields.

Data Quality

Known Limitations

Four structural gaps and caveats in the dataset. None are fixable — they are inherent to how DSN tracking and reentry physics work. Design the dashboard around them, not against them.

Launch Through ~T+3.5 Hours — No Pre-Tracking Data
The dataset begins at 2026-Apr-02 01:59 UTC. The SLS launch, ascent, and early trans-lunar injection (TLI) burn are not covered. Horizons does not provide trajectory data for Orion prior to initial DSN acquisition of signal after orbital insertion. The first row in orion_trajectory represents the earliest point at which JPL had a reconstructed tracking solution available.
Dashboard implication: The trajectory does not begin at Kennedy Space Center or the launch pad. The earliest visualizable position is already in Earth orbit or early trans-lunar coast.
Final ~13 Minutes — Reentry Plasma Blackout
The dataset ends at 2026-Apr-10 23:54 UTC. During atmospheric reentry, the plasma sheath surrounding the capsule blocks all radio communication, including DSN tracking. There is no trajectory data for the reentry corridor from approximately Entry Interface (EI) through splashdown.
Dashboard implication: The trajectory terminates before reaching Earth's surface. The endpoint should be labeled "Last Known Position" — not splashdown.
Ephemeris Is a Reconstruction, Not a Prediction
For active or recently completed missions, Horizons data reflects JPL's best current trajectory reconstruction based on available DSN tracking data. Early in the mission, the solution is updated as additional tracking passes are incorporated. Data fetched at different times during or after the mission may differ slightly for overlapping windows.
Dashboard implication: Re-running scripts/init_db.py after mission end may return a refined trajectory. The dataset is reproducible but not strictly time-invariant.
Coordinate Frame Is Inertial, Not Earth-Fixed
ICRF is a non-rotating frame. Earth rotates inside it. X/Y/Z coordinates are not tied to geographic features — a spacecraft directly over New York will not have a constant X/Y position as time passes. Converting to geographic coordinates (latitude, longitude, altitude) requires accounting for Earth's rotation via Greenwich Apparent Sidereal Time (GAST/GMST).
Dashboard implication: The 2D trajectory visualization uses ICRF X/Y directly (projected into the orbital plane) — this is valid for the Earth-Moon geometry view but does not represent sub-satellite ground track.
Reproducibility

Rebuild Dataset

The database is a reproducible artifact. Run scripts/init_db.py to re-fetch from Horizons and rebuild artemis2.duckdb from scratch. Query parameters in config.py define the dataset — do not modify them without understanding the downstream effects on the DB schema and all derived views.

config.py — Horizons query constants 
# config.py values used for this dataset
SPACECRAFT_ID = "-1024"
MISSION_START = "2026-Apr-02 01:59"
MISSION_STOP  = "2026-Apr-10 23:54"
STEP_SIZE     = "1m"
CENTER        = "500@399"
REF_SYSTEM    = "ICRF"
REF_PLANE     = "FRAME"
OUT_UNITS     = "KM-S"
VEC_TABLE     = "3"
Note: Re-fetching late in or after the mission may return a slightly updated trajectory solution if JPL has refined their tracking reconstruction. The endpoint timestamps are fixed and will not change — but intermediate position values may drift slightly between fetch dates as JPL incorporates additional DSN tracking data.
